# 커밋 메시지 규칙

이 문서는 IPEDS-downloader 프로젝트의 커밋 메시지 작성 규칙을 정의합니다. **Claude는 모든 커밋 시 이 규칙을 반드시 준수해야 합니다.**

## 커밋 메시지 형식

### 기본 구조
```
[타입] 제목

- 변경사항 1
- 변경사항 2
- 변경사항 3
- 변경사항 4
```

### 필수 규칙
1. ✅ **제목**: 대괄호로 감싼 타입과 함께 간결한 제목 작성
2. ✅ **본문**: 불릿 포인트로 변경사항 나열 (최대 4개)
3. ✅ **서명**: Claude 서명은 제외 (Co-authored-by 등 자동 서명 제거)
4. ✅ **언어**: 제목과 본문 모두 한글 사용
5. ✅ **빈 줄**: 제목과 본문 사이에 빈 줄 추가

## 커밋 타입

### 주요 타입
- `[FEAT]`: 새로운 기능 추가
- `[FIX]`: 버그 수정
- `[DOCS]`: 문서 수정
- `[STYLE]`: 코드 포맷팅, 세미콜론 누락 등 (기능 변경 없음)
- `[REFACTOR]`: 코드 리팩토링 (기능 변경 없음)
- `[TEST]`: 테스트 코드 추가 또는 수정
- `[CHORE]`: 빌드 작업, 패키지 관리 등

### 타입 선택 가이드
- **새로운 파일/기능 추가**: `[FEAT]`
- **기존 코드 수정 (버그)**: `[FIX]`
- **기존 코드 개선 (리팩토링)**: `[REFACTOR]`
- **문서만 변경**: `[DOCS]`
- **설정 파일 변경**: `[CHORE]`

## 작성 예시

### 좋은 예시

#### 기능 추가
```
[FEAT] IPEDS 데이터 다운로드 기능 구현

- requests 라이브러리를 사용한 HTTP 다운로드 기능 추가
- 연도별 데이터 필터링 기능 구현
- 다운로드 진행상황 표시 기능 추가
- 에러 핸들링 및 재시도 로직 구현
```

#### 버그 수정
```
[FIX] 파일 저장 경로 오류 수정

- Windows 환경에서 경로 구분자 문제 해결
- 존재하지 않는 디렉토리 자동 생성 기능 추가
- 파일명 특수문자 처리 로직 개선
```

#### 문서 작성
```
[DOCS] 프로젝트 코딩 규칙 문서 작성

- 문서 작성 언어 및 파일명 규칙 정의
- 프로젝트 폴더 구조 가이드 추가
- Python 코딩 스타일 가이드 작성
- 커밋 메시지 규칙 문서 작성
```

#### 리팩토링
```
[REFACTOR] 데이터 처리 함수 모듈화

- 중복 코드 제거 및 함수 분리
- 변수명 가독성 개선
- 타입 힌트 추가
```

#### 설정 파일
```
[CHORE] 프로젝트 초기 구조 설정

- .claude, docs, scripts 폴더 생성
- 코딩 규칙 및 커밋 규칙 문서 추가
```

### 나쁜 예시
```
# ❌ 타입이 없음
데이터 다운로드 기능 추가

# ❌ 영어로 작성
[FEAT] Add data download feature

# ❌ 불릿 포인트 없이 장황하게 작성
[FEAT] 데이터 다운로드 기능
이번 커밋에서는 IPEDS 데이터를 다운로드하는 기능을 추가했습니다.
requests를 사용했고, 에러 처리도 했습니다. 파일 저장도 됩니다.

# ❌ 너무 많은 변경사항 (5개 이상)
[FEAT] 여러 기능 추가

- 기능 1
- 기능 2
- 기능 3
- 기능 4
- 기능 5
- 기능 6

# ❌ Claude 서명 포함
[FEAT] 기능 추가

- 새로운 기능 구현

Co-authored-by: Claude <claude@anthropic.com>
```

## 변경사항 작성 가이드

### 효과적인 불릿 포인트 작성
- **구체적으로**: "버그 수정" 보다는 "파일 경로 오류 수정"
- **간결하게**: 한 줄로 핵심만 전달
- **기술적으로**: 어떤 기술/방법을 사용했는지 명시
- **결과 중심**: 무엇을 했는지보다 무엇이 개선되었는지

### 불릿 포인트 개수
- **최소**: 1개 (작은 변경)
- **권장**: 2-3개 (일반적인 커밋)
- **최대**: 4개 (복잡한 변경)

⚠️ 4개를 초과하는 경우 커밋을 분리하는 것을 고려하세요.

## 커밋 크기

### 이상적인 커밋
- 하나의 논리적 변경사항
- 관련된 파일들만 포함
- 독립적으로 테스트 가능
- 리뷰하기 적당한 크기

### 피해야 할 커밋
- 여러 기능을 한 번에 커밋
- 관련 없는 파일들을 함께 커밋
- 너무 큰 변경사항 (1000줄 이상)

## 브랜치별 커밋 전략

### Feature 브랜치
- 기능 개발 단위로 커밋
- 완성되지 않은 코드도 커밋 가능 (WIP 표시)

### Main 브랜치
- 완전히 동작하는 코드만 커밋
- 모든 테스트가 통과한 상태

## Claude 커밋 시 체크리스트

커밋하기 전 반드시 확인:
- [ ] 커밋 타입이 올바르게 지정되었는가? ([FEAT], [FIX], [DOCS] 등)
- [ ] 제목이 한글로 작성되었는가?
- [ ] 제목과 본문 사이에 빈 줄이 있는가?
- [ ] 변경사항이 불릿 포인트로 작성되었는가?
- [ ] 변경사항이 4개 이하인가?
- [ ] 각 변경사항이 구체적이고 명확한가?
- [ ] Claude 서명이 제외되었는가? (Co-authored-by 등)
- [ ] 관련된 파일만 포함되었는가?

## 커밋 명령어 예시

```bash
git commit -m "$(cat <<'EOF'
[FEAT] 새로운 기능 추가

- 변경사항 1
- 변경사항 2
- 변경사항 3
EOF
)"
```

⚠️ **중요**: HEREDOC을 사용하여 멀티라인 커밋 메시지를 작성하고, Claude 서명은 반드시 제외합니다.
